# Document Preview Capability Flags Plan

## Goal

Make Coneshare usable on both higher-capacity self-hosted deployments and small self-hosted machines by separating document availability from heavy preview generation, and by enabling expensive preview capabilities explicitly.

The current bottleneck is the preview pipeline:

1. Office file -> PDF conversion.
2. PDF -> page image generation.
3. Persisting page images for preview, watermarking, and page-level analytics.

This can require enough CPU and memory that the recommended deployment is around 4 CPU cores and 8 GB RAM. That is reasonable for full VDR usage, but it is not friendly to smaller deployments such as 2 CPU cores and 2 GB RAM.

## Proposed Configuration

Prefer capability flags over a binary `DOCUMENT_PROCESSING_MODE=full|lightweight`.

Rationale:

- A binary mode becomes rigid as Coneshare supports more file types.
- Office, video, PSD, CAD, and server-rendered PDF preview have different dependencies and resource profiles.
- Small deployments should get a safe default without needing to understand "full" vs "lightweight" semantics.
- Advanced deployments should enable only the renderers they actually need.

Target `.env.template` settings after PDF.js support is implemented:

```env
PDF_PREVIEW_ENGINE=pdfjs
ENABLE_OFFICE_PREVIEW=false
DOCUMENT_PROCESSING_CONCURRENCY=1
```

Allowed `PDF_PREVIEW_ENGINE` values:

```text
pdfjs
server_pages
```

Future renderer flags should be added only when the related feature is implemented:

```env
ENABLE_VIDEO_PREVIEW=false
ENABLE_PSD_PREVIEW=false
ENABLE_CAD_PREVIEW=false
```

Do not add unused future flags to `.env.template` yet. Keep the initial surface small.

## Rollout Strategy

Implement this in two main steps. The steps should be kept separate so the first change reduces upload-time resource usage without also changing the viewer, analytics, watermarking, and signed URL model.

### Step 1: Lazy Server-Rendered Preview

Goal: keep the current server-rendered preview experience, but move expensive generation from upload-time to first-view-time.

Scope:

- add `DocumentVersion.render_status` and `render_error`;
- add Django schema migration and data migration;
- stop eager Office/PDF preview generation after upload;
- keep the document/file itself ready after upload;
- mark server-renderable PDF/Office versions as `not_generated`;
- enqueue preview generation automatically when an internal preview, share link preview, or dataroom preview first requests missing page images;
- return pending preview responses while generation is queued or processing;
- add frontend pending UI and polling for existing page-image preview components;
- keep existing server-rendered page viewer, watermarking, and page-level analytics behavior once render is ready;
- make preview enqueue idempotent so concurrent views do not create duplicate render jobs.

This step should not introduce PDF.js. It should preserve the existing server-rendered preview path and only change when preview assets are generated.

### Step 2: PDF.js Preview Path

Goal: add a lower-resource PDF preview path while preserving the server-rendered preview path for deployments that need stronger watermarking and page-level analytics.

Scope:

- add `PDF_PREVIEW_ENGINE=pdfjs|server_pages`;
- add `ENABLE_OFFICE_PREVIEW=false|true`;
- expose `preview_mode` from preview APIs;
- add a PDF.js frontend viewer for `preview_mode=client_pdf`;
- return short-lived signed PDF URLs for PDF.js preview;
- reimplement basic PDF.js analytics without changing server-rendered analytics;
- support visual watermark overlays in PDF.js, but document them as best-effort;
- ensure `PDF_PREVIEW_ENGINE=server_pages` continues to use the existing page-image viewer and lazy server-rendered lifecycle from Step 1;
- keep Office files download-only unless `ENABLE_OFFICE_PREVIEW=true` and `PDF_PREVIEW_ENGINE=server_pages`.

This step can change the default preview engine to PDF.js after the server-rendered lazy path is stable.

### Shared API Contract

Step 1 should already move the preview API toward the final response shape so Step 2 can add PDF.js without another broad frontend rewrite:

```json
{
  "preview_mode": "server_pages",
  "render_status": "processing",
  "preview_status": "processing",
  "pages": [],
  "pdf_url": null,
  "download_url": "https://..."
}
```

In Step 1, `preview_mode` will usually be `server_pages`, `image`, or `download_only`. In Step 2, PDFs can also return `client_pdf`.

## Product Semantics

### Default Preview Path

The default deployment should be low-resource friendly:

- PDF uses PDF.js/client-side preview.
- Images use direct image preview.
- Office files are download-only.
- Unsupported files are download-only.
- Server-rendered page images are not generated by default.
- Office -> PDF conversion is disabled by default.

This means a 2 CPU / 2 GB RAM deployment can still use core Coneshare workflows without running LibreOffice or PDF page rendering by default.

### Optional Server-Rendered PDF Preview

When:

```env
PDF_PREVIEW_ENGINE=server_pages
```

Coneshare supports server-rendered PDF page images. This enables the stronger preview path:

- server-rendered page preview;
- stronger preview watermarking;
- page-level analytics based on server-rendered pages;
- dataroom/share-link page image preview.

Important behavior:

- PDF upload should not immediately generate page images.
- The file should become usable quickly.
- Server-rendered preview generation should be lazy and automatic when the document is first viewed.

### Optional Office Preview

When:

```env
ENABLE_OFFICE_PREVIEW=true
```

Office files can be converted through the heavy pipeline:

```text
Office -> PDF -> server-rendered page images
```

This requires deployment dependencies such as LibreOffice and enough CPU/memory for conversion.

Office preview should only be meaningful when the server-rendered page pipeline is available. If `ENABLE_OFFICE_PREVIEW=true` but `PDF_PREVIEW_ENGINE=pdfjs`, startup validation should either reject the config or warn and treat Office files as download-only. Recommended policy: reject invalid combinations during startup.

### Future Renderer Flags

Future heavy preview types should follow the same pattern:

```env
ENABLE_VIDEO_PREVIEW=false
ENABLE_PSD_PREVIEW=false
ENABLE_CAD_PREVIEW=false
```

Each flag should map to a concrete renderer dependency and resource profile. Do not group them behind a broad mode.

## Preview Strategy by File Type

| File type | Default config | With server renderer enabled |
| --- | --- | --- |
| Image | direct image preview | direct image preview |
| PDF | PDF.js/client-side preview | on-demand server-rendered page images |
| Office | download-only | on-demand Office -> PDF -> page images if `ENABLE_OFFICE_PREVIEW=true` |
| Video | download-only | future renderer if enabled |
| PSD | download-only | future renderer if enabled |
| CAD | download-only | future renderer if enabled |
| Unsupported files | download-only | download-only |
| Oversized files | download-only | download-only or preview unavailable |

## Server-Rendered Preview Lifecycle

### Upload

When a user uploads a PDF while server-rendered preview is active, or an Office document with valid Office preview enabled:

1. Store the original file.
2. Create `Document` and `DocumentVersion` records.
3. Mark the file itself as ready for normal document operations.
4. Do not immediately run Office conversion or page image generation.
5. Set `render_status` to `not_generated`.

Recommended distinction:

- `document.status` should describe file availability.
- `render_status` should describe server-rendered preview asset availability.

Do not overload `download_only` to mean "preview not generated yet."

### First Preview Access

When a server-rendered document is opened in an internal preview, share link preview, or dataroom preview:

1. If render is already ready, return page data.
2. If render is `not_generated`, enqueue render generation automatically.
3. If render is `queued` or `processing`, return a pending response.
4. UI displays "Preparing document preview" with a download fallback.
5. Frontend polls until render is ready.
6. Once ready, display server-rendered page images.

This should be automatic. Users should not need to manually click "Generate preview" for the normal flow.

### Share Link and Dataroom Access

External share link and dataroom visits may automatically trigger render generation when server-rendered preview is enabled.

Reasoning:

- Coneshare is primarily self-hosted.
- Deployments are typically controlled by the owner.
- The expected product behavior is that a recipient can open a link and view the document.
- Requiring the owner to pre-generate previews creates poor UX.

Guardrails are still required:

- enqueue at most one render generation task per document version;
- make task triggering idempotent;
- obey file size and max page limits;
- obey worker concurrency limits;
- do not retry failed renders infinitely;
- provide download fallback while preview is unavailable.

## Client PDF Preview Lifecycle

### Preview

When `PDF_PREVIEW_ENGINE=pdfjs`, PDF preview should use the client-side path:

- preferred: PDF.js/client-side PDF preview;
- fallback: browser-native PDF viewer with a signed URL;
- final fallback: download-only.

PDF.js is preferred over a plain iframe because:

- UI can be more consistent with Coneshare's viewer;
- current page can be tracked at a best-effort level if needed;
- zoom/page navigation can be controlled;
- it avoids server-side PDF -> image conversion.

Limitations:

- PDF.js shifts CPU/memory cost to the client browser.
- It does not support Office files without conversion.
- Page-level analytics are possible only when the user views the file through the Coneshare PDF.js viewer.
- If the user opens the signed PDF URL directly or the browser-native viewer is used, page-level analytics are not available.
- Visual watermark overlays are possible, but they are not strong watermark protection.
- Overlay watermarks can be bypassed with devtools or by opening the signed PDF URL directly.
- Page-level analytics and watermarking in PDF.js mode should not be promised as equivalent to server-rendered preview.

## Suggested Render State Model

Add a render-specific state, separate from `Document.status`.

The main purpose is to separate file availability from server-rendered preview asset availability:

- `Document.status` answers: can the document record/file be used?
- `DocumentVersion.render_status` answers: are server-rendered preview assets available for this version?
- API `preview_status` answers: can the preview UI render the expected preview experience right now?

This distinction becomes necessary once upload no longer eagerly generates preview assets.

Recommended values:

```text
unavailable
not_generated
queued
processing
ready
failed
```

Possible meaning:

- `unavailable`: preview is not supported for this file or mode.
- `not_generated`: preview is supported but has not been generated yet.
- `queued`: preview generation task has been queued.
- `processing`: worker is generating preview assets.
- `ready`: preview assets exist and can be served.
- `failed`: preview generation failed.

This avoids abusing existing fields:

- `document.status=ready` should mean the file is usable.
- `download_only=true` should mean the document cannot use controlled preview and should be downloaded.
- `render_status` should describe server-rendered preview asset availability.
- API `preview_status` should describe effective preview readiness for the current mode.

Do not use `download_only=true` to represent "preview not generated yet." With server-rendered preview enabled, a newly uploaded PDF or Office file may be preview-capable but not generated yet. Marking it as download-only would incorrectly affect share-link behavior, UI states, and later transition logic.

Do not rely only on `has_pages=false`. That boolean cannot distinguish between:

- preview not generated yet;
- preview queued;
- preview processing;
- preview failed;
- preview unsupported by the enabled preview capabilities;
- PDF.js/client-side preview that does not need server-rendered pages.

### Recommended Storage Location

Store `render_status` on `DocumentVersion`, not `Document`.

Reasoning:

- preview assets belong to a specific file version;
- old versions may already have generated previews;
- a newly uploaded version may start as `not_generated`;
- share links and dataroom documents resolve to the current primary version;
- version-level state avoids mixing preview state across document versions.

Possible model addition:

```python
class DocumentVersion(BaseModel):
    render_status = models.CharField(
        max_length=20,
        choices=[
            ('unavailable', 'Unavailable'),
            ('not_generated', 'Not generated'),
            ('queued', 'Queued'),
            ('processing', 'Processing'),
            ('ready', 'Ready'),
            ('failed', 'Failed'),
        ],
        default='not_generated',
    )
    render_error = models.TextField(blank=True)
```

```text

```

```text

```

Worker succeeds:

```text

version.has_pages = true
```

```text
version.render_status: processing -> failed
version.render_error = "..."
```

### Preview Mode

`render_status` describes the server-rendered asset lifecycle, but it does not describe how the file will be rendered. The API should also expose a `preview_mode` and an effective `preview_status`.

Suggested values:

```text
server_pages
client_pdf
image
download_only
```

`preview_mode` can be computed from preview engine settings, enabled renderer flags, document type, size limits, and version state. It does not necessarily need to be stored unless later implementation needs persistence.

Examples:

Server-rendered PDF before generation:

```json
{
  "preview_mode": "server_pages",
  "render_status": "not_generated",
  "preview_status": "not_generated"
}
```

Server-rendered PDF after generation:

```json
{
  "preview_mode": "server_pages",
  "render_status": "ready",
  "preview_status": "ready",
  "pages": []
}
```

PDF.js PDF:

```json
{
  "preview_mode": "client_pdf",
  "render_status": "not_generated",
  "preview_status": "ready",
  "pdf_url": "https://..."
}
```

Download-only Office:

```json
{
  "preview_mode": "download_only",
  "render_status": "unavailable",
  "preview_status": "unavailable",
  "download_url": "https://..."
}
```

### Idempotent Enqueue Rules

Preview generation must be idempotent because multiple users may open the same share link or dataroom document at the same time.

Suggested behavior:

```python
if render_status == 'not_generated':
    set render_status = 'queued'
    enqueue_preview_generation(version)
elif render_status in ['queued', 'processing', 'ready']:
    do_nothing()
elif render_status == 'failed':
    do_not_auto_retry_forever()
```

Retry after `failed` should be an explicit owner/admin action, or a bounded retry controlled by worker policy.

## API Behavior

### Internal Preview

Existing endpoint:

```http
GET /api/v1/documents/{document_id}/preview-data/
```

Server-rendered preview behavior:

- if preview ready: return page image data;
- if preview not generated: enqueue task and return pending response;
- if queued/processing: return pending response;
- if failed: return failed response with download fallback;
- if unsupported/too large: return unavailable/download-only response.

PDF.js/default preview behavior:

- images: return direct image preview data;
- PDFs: return PDF.js/client preview payload, such as a signed PDF URL;
- Office/unsupported: return download-only/unavailable response.

### Public Share Link / Dataroom Preview

Server-rendered preview enabled:

- external access can trigger preview generation automatically;
- page-image preview becomes available after processing;
- page-level analytics and preview watermarking are available only after server-rendered preview is ready.

PDF.js/default preview:

- PDF preview uses client-side/native preview where possible;
- Office documents are download-only;
- PDF.js preview may support best-effort page-level analytics;
- PDF.js preview may support visual watermark overlays;
- preview watermarking and page-level analytics are not guaranteed to match server-rendered controls.

## Frontend UX

### Frontend Contract

Frontend preview components should be capability-agnostic. They should not branch directly on `.env` settings such as `PDF_PREVIEW_ENGINE` or `ENABLE_OFFICE_PREVIEW`.

The backend should resolve preview engine settings, enabled renderer flags, file type, preview state, and limits into response fields:

- `preview_mode`
- `render_status`
- `preview_status`
- `pages`
- `pdf_url`
- `download_url`
- `message`

Frontend behavior should be driven by those fields:

```javascript
if (preview_mode === 'server_pages' && preview_status === 'ready') {
  renderPageImageViewer();
}

if (preview_mode === 'server_pages' && ['queued', 'processing'].includes(preview_status)) {
  renderPreparingPreview();
}

if (preview_mode === 'client_pdf' && preview_status === 'ready') {
  renderPdfJsViewer();
}

if (preview_mode === 'download_only' || preview_status === 'unavailable') {
  renderDownloadFallback();
}
```

Admin/system pages may expose active preview settings, but preview viewers should not depend on them directly.

### Server-Rendered Preview

When preview is pending:

```text
Preparing document preview.
You can download the file while the preview is being generated.
```

Behavior:

- show loading/pending state;
- show download fallback;
- poll preview endpoint until ready;
- render page images when ready.

Polling strategy:

```text
0-30s: poll every 2s
30s-180s: poll every 10s
after 180s: stop automatic polling and show stable fallback
```

If `preview_status=failed`, stop polling immediately and show failure fallback.

After automatic polling stops, the backend task should continue running. The user can download the file, refresh status manually, or return later.

Optional owner/admin action:

- `Regenerate preview`
- `Retry preview generation`
- `Pre-generate preview`

These are secondary actions, not the normal user flow.

### PDF.js / Default Preview

PDF:

- render through PDF.js where possible;
- fallback to browser-native PDF viewer;
- fallback to download.

The default PDF.js path should usually avoid pending preview states:

- PDF should return `preview_mode=client_pdf` and `preview_status=ready`.
- Image should return `preview_mode=image` and `preview_status=ready`.
- Office should return `preview_mode=download_only` and `preview_status=unavailable` when `ENABLE_OFFICE_PREVIEW=false`.

If the default PDF.js path unexpectedly returns `queued` or `processing`, the frontend may use a short fallback window:

```text
0-15s: poll every 3s
after 15s: stop automatic polling and show download fallback
```

Office:

```text
Preview generation is disabled for this file type. Download the file to view it locally.
```

## Resource Guardrails

All preview paths should respect runtime dynamic settings:

- `MAX_PREVIEW_FILE_SIZE_MB`
- `MAX_PREVIEW_PAGES`
- storage quota

These limits already belong in `backend/core/settings_registry.py`, so they should remain runtime-configurable from dynamic settings rather than `.env`.

Settings that require process restart or affect worker topology can live in `.env`, for example:

- `PDF_PREVIEW_ENGINE`
- `ENABLE_OFFICE_PREVIEW`
- document worker concurrency
- conversion timeout
- queue routing

Server-rendered preview should also ensure:

- preview task enqueue is idempotent;
- duplicate page generation does not occur for the same version;
- task retries are bounded;
- failed state is visible and recoverable.

Step 1 does not require `PDF_PREVIEW_ENGINE` yet. During Step 1, the existing server-rendered preview path remains active, but render generation becomes lazy.

Target `.env` settings after Step 2:

```env
PDF_PREVIEW_ENGINE=pdfjs
ENABLE_OFFICE_PREVIEW=false
DOCUMENT_PROCESSING_CONCURRENCY=1
```

Runtime dynamic settings remain managed through admin/dynamic settings:

```text
MAX_PREVIEW_FILE_SIZE_MB
MAX_PREVIEW_PAGES
```

For advanced server-rendered preview deployments:

```env
PDF_PREVIEW_ENGINE=server_pages
ENABLE_OFFICE_PREVIEW=true
```

If `ENABLE_OFFICE_PREVIEW=true`, `PDF_PREVIEW_ENGINE` should be `server_pages`. Office preview depends on the server-rendered PDF/page pipeline. Reject or warn on invalid combinations such as:

```env
PDF_PREVIEW_ENGINE=pdfjs
ENABLE_OFFICE_PREVIEW=true
```

## Implementation Steps

### Step 1: Lazy Server-Rendered Preview

This step changes the timing of the existing server-rendered preview pipeline. It should not introduce PDF.js or change the default preview engine.

Backend scope:

1. Add `render_status` and `render_error` to `DocumentVersion`.
2. Add Django schema migration and data migration.
3. Avoid using `download_only` for "preview not generated yet."
4. Change upload finalize path so PDF/Office files do not immediately run preview tasks.
5. Mark server-renderable PDF/Office versions as `not_generated`.
6. Keep image preview immediate.
7. Keep unsupported/oversized files download-only or unavailable.
8. Add a service function to enqueue preview generation idempotently.
9. Call it from internal preview endpoint when server-rendered preview is missing.
10. Call it from share link/dataroom preview endpoint when server-rendered preview is missing.
11. Return pending responses with download fallback while render is queued or processing.

Frontend scope:

1. Support pending preview state in existing preview components.
2. Poll preview endpoints until render becomes `ready`.
3. Render existing server-rendered page images when ready.
4. Preserve existing server-rendered watermarking and page-level analytics behavior.
5. Show download fallback for pending, failed, unavailable, and oversized files.

Migration note: schema change required for `render_status` and `render_error`.

### Migration Strategy

Use a Django schema migration plus data migration.

Add fields to `DocumentVersion`:

```python
render_status = models.CharField(...)
render_error = models.TextField(blank=True)
```

Backfill `render_status` from existing data:

| Existing state | `render_status` |
| --- | --- |
| `version.has_pages = true` | `ready` |
| image document with `document.status = ready` | `ready` |
| `document.download_only = true` | `unavailable` |
| `document.status = processing` | `processing` |
| `document.status = error` | `failed` |
| `document.status = uploading` | `queued` |
| ready PDF/Office without pages | `not_generated` |

Django migration execution is already once-only. Applied migrations are recorded in the `django_migrations` table, so repeated `python manage.py migrate` runs will not re-run the same `RunPython` operation.

Still write the backfill as idempotent-ish logic:

- compute `render_status` from current row state;
- update the row to the computed value;
- do not append strings, create duplicate side records, or perform external side effects.

Recommended `RunPython` shape:

```python
migrations.RunPython(
    backfill_render_status,
    reverse_code=migrations.RunPython.noop,
)
```

Use `noop` for reverse because this is a one-time state inference. Rolling back the schema removes the field; resetting statuses in reverse does not add value and could destroy useful state during local rollback/reapply workflows.

### Step 2: PDF.js Preview Path

This step adds a new PDF preview path while preserving the server-rendered path from Step 1.

Backend scope:

1. Add `PDF_PREVIEW_ENGINE=pdfjs|server_pages` to `.env.template`.
2. Add `ENABLE_OFFICE_PREVIEW=false|true` to `.env.template`.
3. Add setting parsing and startup validation.
4. Reject or warn when `ENABLE_OFFICE_PREVIEW=true` and `PDF_PREVIEW_ENGINE=pdfjs`.
5. Return `preview_mode=client_pdf` and a short-lived signed PDF URL when PDF.js preview is active.
6. Return `preview_mode=server_pages` and the existing lazy server-rendered response when server-rendered preview is active.
7. Keep Office download-only when `ENABLE_OFFICE_PREVIEW=false`.

Frontend scope:

1. Add PDF.js-based viewer for `preview_mode=client_pdf`.
2. Keep existing page-image viewer for `preview_mode=server_pages`.
3. Reimplement basic PDF.js page-view analytics without changing server-rendered analytics.
4. Add best-effort visual watermark overlay support for PDF.js if needed.
5. Keep fallback behavior for direct signed URL/browser-native PDF viewer/download.

Operational/docs scope:

1. Add deployment docs comparing preview capabilities and resource requirements.
2. Document that PDF.js watermarking and analytics are weaker than server-rendered controls.
3. Document short signed URL expiration expectations for public share/dataroom preview.

## Decisions

- Store `render_status` on `DocumentVersion`. Server-rendered preview assets belong to a specific file version. API `preview_status` should remain an effective UI state computed from preview capability settings, file type, and render state.
- Implement in two steps: first lazy server-rendered preview, then PDF.js. Step 1 should not introduce PDF.js or change the default preview engine.
- Use preview-path-specific pending polling windows. Server-rendered preview polls every 2 seconds for the first 30 seconds, then every 10 seconds until 180 seconds, then stops automatic polling and shows a stable fallback. The PDF.js path should normally avoid pending states; if queued/processing appears, poll every 3 seconds for up to 15 seconds, then show download fallback. Failed previews stop polling immediately.
- When `ENABLE_OFFICE_PREVIEW=false`, Office preview is intentionally unavailable and Office files are download-only. Teams that need Office preview should enable the Office renderer and server-rendered page pipeline.
- Public share link and dataroom PDF.js preview should use short-lived signed PDF URLs in the first implementation. This keeps the lightweight path simple and avoids backend PDF streaming work.
- A backend proxy endpoint can be revisited later if stronger per-request authorization, audit control, or storage URL hiding becomes necessary.
- PDF.js preview may include basic page-level analytics and visual watermark overlays, but these are best-effort capabilities. They should not be marketed as equivalent to server-rendered page analytics or server-rendered preview watermarking.

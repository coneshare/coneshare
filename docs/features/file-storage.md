## Design decisions
- Decision: Separate metadata/control-plane logic (Django) from file I/O data-plane logic (Go file service).
  Rationale: Improves security boundaries and keeps backend API workers focused on business logic.
  Tradeoff: Requires inter-service token and URL orchestration.
- Decision: Use short-lived signed file URLs generated by internal service calls.
  Rationale: Prevents direct long-lived access to protected document objects.
  Tradeoff: Clients must handle URL expiration and refresh behavior.
- Decision: Support multiple deployment storage topologies behind the same file-service abstraction.
  Rationale: Enables local self-host and object-storage-backed deployments without frontend contract changes.
  Tradeoff: Operational behaviors differ by deployment mode and must be documented clearly.

This document defines Coneshare’s secure file-storage architecture and request flow contracts.

---

## 1. Core Principles

1. Security-first access control for protected files.
2. Clear separation between API business logic and file streaming logic.
3. Scalable upload/download path through dedicated file service.

---

## 2. Service Roles

1. `frontend/`: UI client that orchestrates upload/download calls.
2. `backend/`: Django API for auth, permissions, metadata, and business rules.
3. `core/`: Go file service for upload/download/delete I/O and signed URL handling.

---

## 3. Deployment Storage Topologies

Coneshare supports a common logical contract with deployment-specific storage backends.

### Mode A: Local/shared-volume self-host

- File service writes/reads files from mounted storage path (for example `/storage`).
- Common in Docker Compose local/self-host setups.

### Mode B: Object-storage-backed deployment

- File service and processing paths operate against object storage-compatible backends.
- Signed URL and storage-key contract remains stable for clients.

Policy:

- Frontend/backend must not assume one physical storage backend.
- All access should go through file-service/storage abstractions.

---

## 4. Secure Access Pattern (Signed URL Method)

### Upload flow

1. Client requests upload intent:
   - `POST /api/v1/uploads/document/request/`
2. Backend validates policy/permissions and requests upload URL from file service.
3. Backend returns signed upload URL + storage key.
4. Client uploads file directly to signed URL.
5. Client finalizes upload:
   - `POST /api/v1/uploads/document/finalize/`
6. Backend creates metadata records and triggers async processing.

### Download/preview flow

1. Client requests preview/download metadata from backend endpoint.
2. Backend validates permissions and requests signed download URLs from file service.
3. Backend returns signed URLs in response payload.
4. Client/browser fetches file bytes directly from file-service path.

---

## 5. Signed URL Security Contract

Required policy:

1. Signed URLs must be short-lived (explicit TTL configured per environment).
2. Tokens/URLs must be scoped to operation (`upload` vs `download`) and storage key.
3. Replay behavior must be explicitly defined:
   - single-use for upload URLs where supported/recommended,
   - bounded re-use window for download URLs if required by rendering behavior.
4. Invalid/expired tokens must return access denial.
5. Token creation and failed validation events should be audit-loggable.
6. Internal file-service API must be authenticated (service token/mTLS/etc. per deployment policy).

---

## 6. Public vs Protected Assets

1. Public assets (for example avatars) may be served directly by web tier where policy allows.
2. Protected documents/pages must be served only through authorized signed-URL flow.
3. Backend should not expose stable direct filesystem/object paths for protected content.

---

## 7. Configuration Surface

Typical service-level settings include:

- Backend:
  - `CORE_API_URL`
  - internal service auth token/key
- File service:
  - storage root/path or object-storage connection config
  - signing secret/key
  - signed URL TTL policy

Do not commit secrets. Keys/tokens must be environment-managed.

---

## 8. Django FileService Client

Django uses a client abstraction for internal file-service calls.

- Suggested file: `backend/documents/fileserver.py`
- Typical operations:
  - generate upload URL
  - generate download URL
  - delete file

Contract requirement:

- Client should return URLs suitable for caller context while preserving security constraints.

---

## 9. Reverse Proxy Routing

Web tier routes:

1. File paths (for example `/files/`) -> Go file service.
2. API paths (for example `/api/`) -> Django backend.

API path policy:

- Application endpoints should remain versioned (`/api/v1/...`) even if proxy route is broader (`/api/`).

---

## 10. Testing and Operations Scope

Security tests:

- expired/invalid signed URL rejection
- operation mismatch rejection (upload token used for download, etc.)
- storage-key scope enforcement

Integration tests:

- request-upload-finalize flow
- preview/download signed URL generation and fetch behavior
- delete-file behavior and metadata consistency

Operational checks:

- token TTL configuration validation
- file-service auth connectivity checks
- audit logging coverage for token lifecycle events
